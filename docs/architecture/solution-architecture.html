Hackfest'26 · Last Mile · Response to technical review

How Last Mile is put together, and who is allowed to see what

The same architecture as before, with three changes the review asked for: three real roles instead of one manager and a read-only guest, every console explained top to bottom, and data stores drawn with arrows of their own so a read is never mistaken for a write.

What is built, and the one thing that is not

Everything on this page runs today, including the three-role model: admin, collections manager and collection agent, each gated on every page and every API call. A collection agent sees only the queue assigned to them and may re-order their own work before release. A read-only guest role existed and was withdrawn: it could read the bank configuration and the onboarding console, which a collections manager cannot.

The exception, marked wherever it appears: the agent console does not yet let a collector record what happened on each attempt. The 30-day feedback loop runs; the same-day one cannot until that capture exists. See section 05.

01

The solution, end to end

One frame. The bank already has a prediction; everything below it is the part that turns that prediction into an approved action. Read it downwards — and note that the three boxes in the middle are answered independently, which is what separates this from a sorted list.

Why the three run in parallel

If policy were applied after scoring, a suppressed account could still influence the allocation by consuming capacity in the solver. Gating first means the optimiser never sees an action it is not allowed to take, and the plan is feasible by construction rather than by correction.

Why the value step is plain arithmetic

Combining uplift with money is the moment this becomes a financial decision, and it is the step a reviewer will want to check by hand. Keeping it as one named expression over stamped fields means anyone can recompute a single row on paper.

Why the rules run twice

The gate says what is allowed before optimisation. The verifier re-checks the finished plan afterwards, through different code. Between those two points the optimiser, the packer and a manager's edits can all change the plan — an edit that swaps a 12-minute call for a 45-minute referral is exactly the case the second pass exists for.

03

Three roles, and what separates them

Admin and manager differ by what they may change. The collection agent differs by which rows exist for them at all — a harder thing to build, and the reason this is enforced in the API rather than in the navigation.

Admin

The only role that can change how the system itself behaves.

  • Only they can onboard a bank and see its connection details.
  • Only they can open or save configuration — the rules, the LGD table, the caps.
  • Only they can create manager accounts. Collection-agent accounts can be created by an admin or by a manager, linked to a roster collector id such as C01.
  • Full access to the agent trace and every stored LLM request and response.

Collections manager

Owns the business day. Cannot change the rules they operate under, which is the point.

  • Sets today's team, starts the run, approves, releases, closes the day.
  • Sees every collector's queue, the daily results and the KPIs.
  • Adds collection agents from Users & access and sees the list of their own agents — but cannot create another manager or an admin.
  • No access at all to configuration, onboarding or user management — not even to read.
  • Cannot open a collection agent's queue page.

Collection agent

Sees one thing: the accounts assigned to them today.

  • Their own queue only. Other collectors' queues do not exist for them.
  • May re-order their own work while the run is awaiting approval. The order locks once actions are released, and every re-order is written to the audit chain.
  • Cannot approve, release or re-plan; cannot reach any other console, including the guided tour and the demo.
  • The scoping comes from the signed-in session. A collector id in the URL is ignored.

Signing in sends you somewhere you can open

Every role has a landing page it is allowed to reach: a collection agent goes to /agent, everybody else to the guided tour. A link to a page the role cannot open — a stale bookmark, or a default written for a different role — is corrected at sign-in rather than followed into a permission error. And a refused page answers with a page that says which role the account has and where it can go, not a JSON error in the address bar.

The part that is easy to get wrong, and was done right

Hiding a page from the navigation is not access control. For the collection agent role to mean anything the API has to scope the worklist to the signed-in collector — if the browser can ask for ?collector_id=C03 and get an answer, the role is decoration. In this build the collector id is read from the session on the server and the browser cannot supply one, so the guarantee holds even if someone crafts the request by hand.

05

The feedback loop — two speeds

What the collection agent records comes back into the system. It arrives in two very different ways, and conflating them is the easiest mistake to make here.

Why real-time outcomes do not train the model directly

The uplift model learns from cured_30d — did the account catch up within 30 days of being worked. That label is deliberately withheld until 30 days have passed, so a row cannot be trained on its own outcome. A collector's note at 11am that someone promised to pay is a genuine signal, but it is not that label: promises are broken, and a model trained on promises would learn to predict optimism rather than recovery.

So the collector's feedback does three things instead, all of them real: it updates contact history and reachability, which are model features on the next run; it replaces our fixed 12 / 25 / 45-minute handling estimates with what calls actually took, which makes tomorrow's queues fit; and it raises hard stops — a wrong number, a stated cease-and-desist — that suppress the account immediately rather than a day later.

If a shorter-horizon label is wanted, the honest way to add one is a second outcome the bank can confirm — a payment within 7 days, or a promise actually kept — trained as its own model, not by relabelling what the collector typed.

Fast loop · same day

  • Contact history → contacts_30d, rpc_rate_90d, days_since_last_contact on the next run.
  • Real handling minutes → capacity and packing, which is the measurement gap behind our collector-time KPI.
  • Hard stops → wrong number and cease-and-desist suppress before the next plan.
  • A promised date → do not contact again before it.

Slow loop · 30 days

  • The bank confirms payment and account status.
  • cured_30d is published only once the window closes.
  • A training row is assembled: features as they were on the day, the action taken, the outcome that followed.
  • The model retrains and is promoted only if it beats random on a Qini check. A model that fails validation does not reach a worklist.

What this costs to build

  • The slow loop already runs — it is how the current model is trained.
  • The console is built. What is missing is an outcome-capture endpoint, a table to hold the attempts, and the three feature joins that would read it.
  • Every field it writes has to carry a timestamp and pass the leakage guard, or it will quietly contaminate the training set.

07

Each console, top to bottom

What a person does on the page, what runs underneath, which stores are touched, and what comes back. The chips repeat the access level so a page can be read on its own.

Today · /manager

admin fullmanager fullcollector none
  1. The manager confirms today's team — who is in, and how many minutes each person works.
  2. Start run. The API writes a run row and hands control to the Supervisor; the page follows the stages live.
  3. Eight agents run. Feeds come from the bank, personal data goes to the vault, the plan is optimised and packed into shifts.
  4. A worklist appears, already split into one queue per collector, each provably inside that person's shift.
  5. The manager approves, edits or rejects each item. Anything escalated — hardship, large exposure, a wide uplift interval — has to be looked at individually.
  6. Release posts approved actions to the bank. Close day freezes the report.
  7. If the team changes mid-morning, re-plan rebuilds the queues from the same model run and retires the old worklist.

Stores: reads config packs and the saved roster; writes runs, trace, recommendations, approvals, releases and the audit chain. Opens the identity vault only at release, to write the call script.

My queue · /agent

admin n/amanager nonecollector own only
  1. The collector signs in and sees only the accounts assigned to them today, in the order the optimiser put them.
  2. Each row carries the action, the script, the reason and the figures behind it, plus a running total of assigned, pending and released work.
  3. They can re-order their own queue while the run is awaiting approval — the person on the phone knows things the optimiser does not. The list must still contain exactly their own accounts, once each.
  4. The order locks once actions are released, and every re-order is written to the audit chain as queue.reordered.
  5. They cannot approve, release, re-plan, or see another collector's rows.
  6. The filter is applied server-side from the session. A collector id in the URL is ignored, and an account that is not linked to a roster collector gets a 403 rather than an empty page.

Stores: reads recommendations and releases scoped to that collector; writes queue positions and an audit entry. Not yet: there is no endpoint for recording what happened on an attempt, so nothing from this page feeds the same-day loop. See section 05.

Daily results · /report

admin fullmanager fullcollector none
  1. Pick a business day.
  2. The API rebuilds that day from stored facts, not from live data — the same day always renders the same page.
  3. Shows the team, every run that happened that day including superseded ones, what was recommended against what was released, per-collector queues, and the override reasons managers gave.
  4. Follow-up comes back from the bank: executed, reached, cured at 30 days, amount paid.
  5. The audit chain is verified on load and the result is shown.

Stores: reads SQLite and the run's Parquet artifacts. Writes nothing.

Performance · /kpis

admin fullmanager fullcollector none
  1. Pick a window. Seven cards, one per business question.
  2. Each card states whether it is measured, partly measured or waiting for outcomes — outcomes mature at 30 days, so recent days honestly cannot answer yet.
  3. Every KPI opens into a daily chart, plus four notes: how it is measured, where the numbers come from, how far to trust it, and what is missing.
  4. "Why this customer?" deep-links straight into that account's explanation on Today.

Stores: reads SQLite and the bank's action log. Writes nothing. Carries a standing warning that without a randomised holdout these are observed results, not proven effects.

Runs & pipeline · /admin

admin fullmanager fullcollector none
  1. Every run, with its stages and how long each took.
  2. Every tool call an agent made, in order, with a summary of what went in and what came out.
  3. Every LLM request and response, stored verbatim — the prompt, the reply, the model, and whether the validator accepted it or forced the one rewrite.
  4. The artifacts each stage produced, downloadable for inspection.

Stores: reads runs, trace, llm_calls and Parquet artifacts. Writes nothing.

Bank configuration · /admin/config

admin editmanager nonecollector none
  1. The three YAML packs — scenario, institution, run — each field explained in plain language next to the value.
  2. An edit is checked before it is saved: the schema is validated, the offending line is named, and a diff of what would change is shown.
  3. A manager cannot open this page at all — the route and its API are closed to them, not merely read-only.
  4. On save the pack is re-hashed, and the new hash is stamped onto every run that follows — so a report always says which rules produced it.

Stores: reads and writes the YAML config packs; writes an audit entry per save.

Onboard a bank · /admin/onboarding

admin fullmanager nonecollector none
  1. The admin gives a base URL. The Onboarding Agent reads the bank's own API description.
  2. LLM call one: from the endpoint list, which feeds does Last Mile need, and where are they.
  3. The agent samples those feeds and profiles the columns as value shapes — Aaaaa, +9-999-9999 — never values.
  4. LLM call two: map this bank's columns to the 54 canonical fields, and say whether the risk score is a band or a probability.
  5. Deterministic checks run: does every column exist, do the values match the expected kind, are required fields covered. Failures go back once for a correction.
  6. The admin sees the proposal field by field and approves or rejects. Only on approval is an institution pack written.

Stores: reads the bank's API and samples; writes a proposed config pack and the LLM call record. Nothing is used until an admin approves it.

Users & access · /admin/users

admin every rolemanager agents onlycollector none
  1. Lists the accounts this person is allowed to manage: an admin sees all of them, a manager sees only their collection agents, with the roster collector each one is linked to.
  2. The role dropdown is built from the server's answer, not hard-coded: a manager is offered collection agent and nothing else, and the field is hidden entirely when that is the only choice.
  3. A collection-agent account must carry a collector id from the daily team, such as C01. That link is what gives the person a queue; without it the agent page returns 403.
  4. Passwords are at least 12 characters and are shown once. Accounts live in an app_users table, separate from the bootstrap accounts in the environment, so the first admin can always get in.
  5. Every change records who made it and when, in the audit chain.

The rule that matters: the cap on what a person may grant is enforced in the API, not the dropdown. A manager who posts role: "manager" by hand gets a 403. Stores: reads and writes app_users; passwords held as PBKDF2-SHA256 hashes.

Guided tour, Demo & Presentation · /guide, /demo, /presentation · outside the sidebar

adminmanagercollector none
  1. A plain-language walkthrough of one run, for a client who has not seen the system before.
  2. Technical detail is available on demand rather than shown by default.
  3. Neither page shows customer data. All three were taken out of the sidebar and are reached by URL; a collector account cannot open them.

Stores: reads a completed run for illustration. Writes nothing.

Where an agent decides, where a rule decides, and where a person decides

The review asked us not to use AI where a rule is enough. Here is the split, stated as a responsibility per component rather than as a claim about the system as a whole.

DecisionDecided byWhy that and not something else
May we contact this person at all?ruleConsent, do-not-call, deceased, bankruptcy, litigation, fraud hold. Binary, legally defined, and auditable. A model here would be both useless and indefensible.
Which actions are available for this account?ruleEligibility is written as structured conditions in YAML — days past due thresholds, hardship history, product. An admin can read and change them; nobody has to retrain anything.
Have we contacted them too often?ruleCounting. The cap is 7 attempts in 7 days and 1 contact a day.
How much money is at stake?arithmeticpd_12m × exposure × lgd. Same inputs, same answer, every time, and every input traceable to a bank field.
How much difference would each action make?modelThis is a genuine pattern-finding problem across sixteen signals, and it is the one thing a rule cannot do: no policy can tell you who is persuadable.
Which actions do we actually do today?optimiserA constrained allocation problem — value against capacity, caps and shift lengths. A solver gives the best feasible answer and can prove it is feasible. An LLM would guess.
Who works which account, in what order?optimiserBin packing with a repair step. A 45-minute referral cannot be split across two people, so this has to be exact rather than approximately right.
How should the reason be worded?LLMLanguage, not judgement. It receives segment and action, writes a template with placeholders, and the figures are filled from stamped facts. A validator checks the wording against those facts and allows one rewrite.
How does a new bank's data map to ours?LLM + ruleReading an unfamiliar API and guessing that CURR_BAL means current balance is exactly what a language model is good at. Whether the guess is right is then checked deterministically, and an admin approves it.
Does this action go to a customer?personAlways. Nothing reaches the bank without a manager's release, and every release is in the hash-chained audit with who approved it.

The rule we applied. If the answer is defined by policy or law, it is a rule. If it is arithmetic, it is arithmetic. If it needs a pattern across many weak signals, it is a model. If it is a constrained allocation, it is a solver. The LLM gets the two jobs that are genuinely about language — wording and interpreting an unfamiliar schema — and neither of those outputs is ever a number or a decision.

What happens when something goes wrong

The design rule is fail-closed: when the system cannot be sure, it produces no worklist rather than a doubtful one. A missing worklist costs a day; a wrong one contacts real people.

What goes wrongResultWhat the system actually does
The bank's API is unreachable, or a required feed is missingrun stopsFails before any modelling, naming the feeds that were not published. No partial worklist is ever produced.
A config file is edited while a run is in progressrun stopsRefuses to continue rather than finish under two different sets of rules.
A quality gate fails — too few rows, too many nulls, a stale score, an unknown graderun stopsThirteen gates run before anything is scored. A score older than two days stops the day.
Code asks for a banned column as a featurerun stopsThe leakage guard raises rather than warns, so a leaking model cannot reach a worklist by accident.
History has too little treatment variation to identify upliftrun stopsFeasibility is checked before training: "causal feasibility checks failed; worklist not produced".
The trained model fails its holdout checkrun stopsIf Qini is below the threshold on any action, the run refuses to publish. A model that cannot beat random ranking never reaches a collector.
The finished plan breaks a policy rulerun stopsThe independent verifier writes a plan.rejected audit entry and fails the run, quoting the first violations.
A collector's queue will not fit their shiftdegradesThe packer re-solves at reduced capacity, up to three attempts. Anything that still does not fit is reported as unassigned rather than forced onto someone.
The LLM is unavailable, or its wording fails validationdegradesOne rewrite is attempted, then a deterministic fallback template is used. The recommendation still ships and records which source wrote it. No LLM outage can stop a worklist.
A manager's edit overfills a queueflaggedSwapping a 12-minute call for a 45-minute referral marks the queue over-shift in the console rather than silently accepting it.
The team changes after the plan was builtrecoversRe-plan rebuilds the queues from the same model run, supersedes the old worklist, and records the link between them.
The solver returns a non-optimal statusknown gapThis one does not fail closed. The status is recorded on the run, but the plan is still built from whatever the solver produced. It should refuse, the way the verifier does. Found while writing this page.
