1 · What the system does

A bank already predicts which members may miss payments. Last Mile decides, every business day, who the collections team should contact, how, and why — within each collector's working hours and the bank's rules — and a manager approves every action before anything reaches a member.

1 · TeamManager enters who works today and for how long
2 · Run8 AI agents read bank data, score accounts and build one queue per collector
3 · ReviewManager approves, changes or rejects each recommendation
4 · ReleaseApproved actions are sent to the bank
5 · Close dayReport is frozen; the simulated bank moves to the next day

Words used in this document

RunOne execution of the agents. Has an id like run_20260915T063217_3955. Always note it in results.
Business dayThe bank's date (as of). It only changes when the manager closes the day. It can be ahead of the real calendar.
Roster / teamCollectors, whether each is working, and shift minutes. 90% of each shift is plannable (10% buffer).
QueueThe ordered list of tasks for one collector. Texts (SMS) go to Automated SMS.
EscalatedA recommendation that needs individual review; excluded from bulk approve.
SupersededA worklist replaced by a newer one for the same day (re-plan or new run). Read-only.
SegmentsPersuadable (contact helps), Sure thing (pays anyway), Lost cause (unlikely to pay), Sleeping dog (contact may make it worse), Uncertain.

2 · Scope

In scope

  • Team (roster) entry, validation and carry-forward
  • Starting runs; the 8 stages; failures
  • Worklist, per-collector queues, filters, account review
  • Approve / change / reject / bulk approve
  • Re-plan after a team change
  • Release to the bank; locking
  • Close the day; bank day advance; daily report
  • Admin Console incl. LLM call records
  • Configuration editor: check, save, history, conflicts
  • Governance rules (suppression, contact caps, audit)
  • Layout at phone width, dark mode, performance, error messages

Out of scope

  • Accuracy of the statistical model (covered by automated tests and the benchmark)
  • The /demo page — contains known outdated claims; not a release target
  • Real bank integration, logins and permissions (none exist; everyone is manager.demo / admin.demo)
  • Load testing, security penetration testing
  • Wording quality of Gemini output beyond the checks in ACC-03/04
Priorities. P1 a member could be wrongly contacted, data is wrong or lost, or the main flow is blocked.   P2 a feature does not work but there is a workaround.   P3 cosmetic or minor.
Automated tests exist. Developers run make test (39 tests). Manual testing focuses on what a person sees and does; if you find a rule broken that you think a test should catch, say so in the defect.

3 · Test environment

3.1 Prerequisites

Toolsuv (Python package manager), make, a terminal, Google Chrome (latest). Optional: DB Browser for SQLite for section 6.
ProjectThe kamat folder from the developer
Gemini keyOptional. Ask the developer; needed only for ADM-05/07 and LLM wording checks. Never paste it into a defect.

3.2 First-time setup

cd kamat
make setup          # installs Python 3.11 and dependencies, creates .env
# optional: open .env and set GEMINI_API_KEY=...
make seed           # creates the simulated bank (about 2 seconds)
make up             # starts bank (8001) and engine + consoles (8000); leave this terminal open

3.3 Daily start / stop

Start: make up. Stop: press Ctrl+C in that terminal. After the developer delivers a new build, stop and start again — the servers do not reload code on their own.

3.4 Reset to a clean state

Use before a full test cycle, or when data from earlier testing gets in the way.

Ctrl+C              # stop make up
make seed           # new simulated bank, business day = today's real date
make clean-runs     # deletes all runs, decisions, rosters, reports, audit and LLM records
make up
Reset deletes history. Export or screenshot anything you need as evidence first. make clean-runs does not reset configuration files — use the editor's Earlier versions to restore those (CFG-09).

3.5 Test data

All data is synthetic: 4,000 members, about 1,500 accounts behind on payments, 120 days of history. Names like Morgan Nguyen are fake. Generation is deterministic for a given date: two testers who reset on the same day see the same numbers. Figures quoted in this plan (e.g. 291 recommendations) are examples; yours will differ.

4 · How to run, record and track testing

4.1 Order of execution

Execute areas in this order — later areas need state created by earlier ones: ENV → TEAM → RUN → WL → ACC → DEC → RPL → REL → CLOSE → RPT → ADM → CFG → GOV → OTH → NFR. Run the full P1 set first on day 1; P2/P3 on day 2.

4.2 Recording a result

  1. Tick Pass only if every bullet under Expected is true.
  2. Tick Fail if any bullet is false; raise a defect (template 8.1) and write its id in the Defect line.
  3. Tick Blocked if you could not execute (e.g. bank would not start); note the blocking defect id.
  4. Leave untested cases blank; they count as Not run.
  5. For every run you create, write the run id next to the case (shown in the Manager chips and Admin banner).

6 · Optional database checks

For testers comfortable with SQL. Open the files read-only in DB Browser for SQLite (File → Open Database Read Only). Never edit these files — the audit tables refuse changes by design and editing others corrupts test data. Replace RUN with a run id.

Engine databasekamat/data/engine/lastmile.db
Bank databasekamat/data/bank/bank.db

G1Suppressed accounts in a worklist (expect 0)

-- engine DB: data/engine/lastmile.db. Replace RUN.
SELECT COUNT(*) FROM recommendations
WHERE run_id = 'RUN' AND alternatives_json LIKE '%suppressed:%';

G2Members with more than one contact (expect no rows)

SELECT member_token, COUNT(*) n FROM recommendations
WHERE run_id = 'RUN' GROUP BY member_token HAVING n > 1;

G3Minutes per collector vs shift

SELECT collector_id, COUNT(*) tasks,
       SUM(json_extract(facts_json, '$.minutes.value')) minutes
FROM recommendations WHERE run_id = 'RUN' GROUP BY collector_id;

G4Latest audit events

SELECT seq, run_id, event_type, actor, created_at FROM audit_events ORDER BY seq DESC LIMIT 20;

G5LLM calls of a run

SELECT id, purpose, status, http_status, latency_ms, total_tokens FROM llm_calls WHERE run_id = 'RUN';

G6Bank: actions and how they went (bank DB: data/bank/bank.db)

SELECT ACTION_CD, EXECUTION_STATUS, COUNT(*), SUM(RPC_IND)
FROM collection_actions GROUP BY 1, 2;

7 · Known behaviour that is not a bug

You may seeWhy
Business date ahead of the real calendarEvery Close the day moves the simulated bank forward one day, regardless of the clock.
Most tasks are SMS; few hardship referralsSMS uses no collector time. Payment plans are usually worth more per minute than hardship referrals.
Planned minutes a few below plannable (e.g. 322 of 324)Tasks are 12, 25 or 45 minutes; the leftover minutes cannot fit another task.
Run takes about a minute with GeminiEach Gemini call takes 20–25 seconds; there can be two (draft + rewrite).
Some explanations say fallback templateGemini output that fails the checks, or no key, uses standard wording by design.
Caught up within 30 days: not yet knownOutcomes only exist 30 business days after the actions.
Estimated dollar values look large versus the benchmarkModel estimates are about 2× optimistic; this is documented. Do not log it as a defect.
Re-planned run reuses stages 1, 3 and 4 with 0 msData and model are copied from the parent run on purpose.
Everyone appears as manager.demo / admin.demoThere is no login in this build.
/demo page claims (e.g. fixed ROI, “0 harmful”)Known outdated page, out of scope.
Always a P1 defect, even if it looks small: a suppressed (deceased, bankruptcy, do-not-call…) member recommended; one member with two contacts the same day; a number in an explanation without a source; a surname, phone or email visible outside the bank; a released action that can still be changed; audit chain not verified; a collector's queue over their shift before any manager edits.
